# Архитектурное решение по кешированию

### Мотивация

Клиенты жалуются на производительность работы сервиса
- Сейчас все запросы идут через БД
- Постороные запросы к MES для расчетов выполняются каждый раз
- Загрузка страницы клиента каждый раз просходит полностью заново

Кеширование даст
- Повышение производительности, засчет уменьшение нагрузки на БД, на сервер
- Сокращение объема передаваемых данных
- Ускорение повторных операций

### Предлагаемое решение

[Предлагаемое рещение для кеширование MES для операторов](<Предлагаемое решение.puml>)
 
Для Shop API часть запросов можно закешировать на стороне клиента. 
- список рекомендаций товаров, расчитывать на сервере (раз в N часов/дней) и кешировать в браузере (TTL например день)
- просмотры товаров, отзывы, оценки, также не требуют сверх точного обновления. Эти данные также можно сохранять на клиенте
- историю заказов (упрощенную версию)

При работе с заказами основные проблемы
- Высокая нагрузка на базу данных при каждом запросе
- Необходимость получать актуальные данные в реальном времени
- Конкуренция между операторами за новые заказы

Необходимо внедрить следующие стратегии кеширования

Почему Read Through:
- Операторы должны получать актуальные данные о заказах
- При отсутствии данных в кеше, система автоматически загрузит их из базы
- Автоматическое обновление кеша при запросе

Почему Write Through:
 - При изменении статуса заказа (что происходит часто)
 - Данные одновременно обновляются и в базе, и в кеше - гарантирует актуальность информации для всех операторов

Альтернативные варианты
- Cache Aside - может привести к задержкам при обновлении данных
- Write Behind - не подходит из-за требования мгновенной актуальности
- Write Around - не гарантирует актуальность данных

### Инвализация кеша 

Для стратегии вытеснения можно использовать LRU, так как актуальность заказа напрямую связана с временем создания. 
При этом следуют настроить метрики, для оценки выбранного решения

Метрики для оценки эффективности:
- Hit Rate (процент успешных обращений к кэшу)
- Miss Rate (процент неудачных обращений)
- Average Response Time (среднее время отклика)
- Cache Size (размер используемого кэша)
– Eviction Rate (частота вытеснения данных)
