# Архитектурное решение по логированию

### Мотивация

Логгирование
- Упрощает отладку и поиск ошибок в системе
- Оперативно реагировать на ошибки в системе: распределить сообщения по уровням и настроить автоматический алертинг на ошибки типа FATAL 
- Позволяет отслеживать подозрительную активность в системе
- Анализировать поведение пользователей в системе для оценки эффективности и удобства работы сервисов
- Также для алертинга можно использовать

Исходя из требований требуются покрыть необходимый и наиболее выжный функционал. 
Пользователи жалуются на потерю заказов, что критично для интернет магазина.

Логгирование `ERROR`
- Для ошибок подключения к БД, очереди, др сервисам, таймауты запросов
- Сбои в обработке заказов - нарушение цепочки статусов, некорректные данные, TTL по заказу (например заказ висит > 30d)
- Переполнение очередей заказов

Логгирование `WARNING`
- Неправильные логин/пароль при входе в системуё
- Исключения, которые не мешают основной цепочки заказа, но снижают качество работу продукта
- Долгое время обработки заказа (например несколько дней заказ висит в статусе "начал упаковывать")

### Предлагаемое решение

[Предлагаемое решение](<Предлагаемое решение.drawio>)

Логгирование будет реализовано с помощью стека ELK

Для подключения логгирования необходимо настроить

- Сохранение логов сервисов в фалах `/var/log/[service-name]/.....{.json}`. Настроить stdout на запись в файлы
- Контейнер Filebeat для сбора логов из фалов и их отправки в logstash
- Контейнер Logstash для обработки логов и отправки в elastic search
- Контейнер Elastic Search для хранения и индексирования логов
- Контейнер Kibana для визуализации и работы с логами

Для безопасности 
- Внедрить авторизацию с доступом сотрудникам с ролями "Разработчик" и "Поддержка"
- Фильтрация чувствительных данных
удаление или маскировка персональных данных
исключение токенов, паролей
- Журналирование всех операций в сервисе по работе с трейсингом
- Доступ только под корпоративным VPN

Для масштабирования\
Необходимо разбить логи на уровни hot/warm/cold. Настроить min_age и rollover.max_age, rollover.max_size\
Следует держать индексы не больше 30-50GB. При увелчении объема логгирования cold данные можно хранить на более дешовом оборудовании. \
Пока система небольшая можно ограничиться одним индексом, далее выделять по сервисам и бизнес сущностям (service-crm-api, order и тд)
```
{ 
  "phases" : { 
    "hot" : { 
      "actions" : { 
        "rollover" : { 
          "max_age" : "30d", 
          "max_size" : "50gb" 
        } 
      } 
    }, 
    "warm" : { 
      "min_age" : "45d", 
    }, 
    "cold" : { 
      "min_age" : "60d", 
    }, 
    "delete" : { 
      "min_age" : "90d", 
    } 
  } 
}
```


### Алертинг 

Необходимо настроить алертинг в grafana для быстрого реагирования в критических ситуациях 

- Алертинг на FATAL ошибки.
- Алертинг на аномалии в системе (резкий скачок попыток входа в систему. скачок скачивания логов системы - утечка данных)
- Попытка отправки SQL инъекций и прочего
